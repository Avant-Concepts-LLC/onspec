What comes back

A written report, in PDF and Markdown. Its core looks like this.

sample report · an invented repository
Source: "Invoice export" PRD · 18 requirements · commit 4f2c1e9

SPEC-0001  Invoice export
  ✓ met        C3   Archived invoices are exported when include_archived=true
               test passed: includes archived invoices
  ✗ unmet      C7   Amounts round half-even to two decimals
               src/export/format.ts:41 rounds half-up; no test covers rounding
  ? uncertain  C11  Exporting 50,000 rows completes without error
               no test runs at this size; a load test would decide it

Not checkable as written
  C14  "Export should be fast"
       no pass or fail behavior stated; rewrite proposed

Code no requirement covers
  ⚠ src/admin/bulk-delete.ts
       added in this work; nothing in the spec asks for it

Summary: 12 met · 3 unmet · 2 uncertain · 1 not checkable (18 requirements)
  • Every met or unmet cites its evidence: a test that passed or failed, or a file and line. A verdict that cannot be backed is reported as uncertain. Nothing is guessed.
  • Vague requirements are a finding. "Should be fast" cannot pass or fail. The report lists each one with a rewrite that can.
  • You keep the check. Your spec comes back as onspec files with the CI step, so the same verdicts run on every pull request afterwards. The tool is free and MIT licensed.

What you send

  1. The spec, in whatever form it exists: a PRD, a set of tickets, a statement of work, or the prompt you gave the agent.
  2. Read-only access to the repository, or a zip of it.
  3. The test results your CI already writes (JUnit XML), or the command that runs your tests. No tests is fine. It changes what counts as evidence, and the report says so.

What it is not

  • Not a security audit or a penetration test.
  • Not a review of code quality, performance or architecture.
  • Not a guarantee that the software is right for your business. It answers one question: does the code do what this document says?

How it goes

  1. You email the request: the language and rough size of the repo, where the spec lives, about how many requirements, and when you need it.
  2. You get a yes or no within one business day. A spec with more than 25 requirements, or more than one repository, gets a fixed quote instead.
  3. You get an invoice. Work starts when it is paid and access is given.
  4. The report arrives within five business days. One round of questions about it is included. If it is late, you get your money back.

Who runs it

Ben Subercaseaux, who wrote onspec, at Avant Concepts LLC. One person reads your spec and your code and signs the report. That also means a few reports a month, first come, first served.

Your code

  • Access is read-only and ends when the report is delivered. Local copies are deleted then.
  • Where a requirement has no test behind it, the relevant code and the requirement's text go to the Anthropic API so a model can assess it. Every verdict reached that way is checked against the code by hand before it goes in the report.
  • If no code may go to a model, say so. Those requirements are read by hand instead.
  • An NDA on request, signed before access.

Questions

Can I run this myself?

Yes. npm install -g onspec, and the docs cover the rest. The report is for when you want it done this week, or want the check made by someone who is neither the author of the code nor the agent that wrote it.

My spec is a mess.

Most are. Turning it into requirements that can pass or fail is part of the work, and you keep the result.

Which languages?

Any. Test evidence comes through JUnit XML, which nearly every test runner can write. The rest is read from the code.

What if nothing is unmet?

Then you have that in writing, with the evidence, and the spec files that keep it true.
